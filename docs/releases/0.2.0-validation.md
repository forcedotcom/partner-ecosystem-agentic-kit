# 0.2.0 Beta validation summary

Date: 2026-11-04. Source candidate: `v0.2.0-rc.1`, commit
`68cf4664fd43dd66b4bdcb5bbb796aa2adb1c3f9`.

The maintainer requested promotion after reviewing the before/after comparison
and the native GitHub-backed update. The promotion changes release manifests
and documentation only; it must not silently change the tested skill payload.
Raw captures, private configuration and backups remain outside this public repo.

## Observed maintainer-supervised Claude Code behavior

Claude Code 2.1.318, native response model `claude-opus-5-5`, unchanged owner
provider/configuration, manual permissions, project-scoped installation.
The baseline was an older `0.1.0` payload with 26 skills; the candidate had 27.
The version label alone is therefore not the complete baseline identity.

Seven identical supplied-context prompts were submitted in fresh before/after
sessions, with one additional human approval response in each session:

| Exercise | Observed result |
|---|---|
| Product discovery | Routed to Solution Discovery; bounded first-build advice. |
| Native / API / MCP choice | No external integration recommended solely because a supporting MCP skill exists. |
| Disposable versus retained test data | Separate development and persistent-test recommendations; entitlements remain unverified. |
| Effective package-build definition | Package validation handoff and evidence/override distinctions without real-project inspection. |
| Assess | Only the two authorized synthetic files were read; no edits. |
| Act | A bounded one-field edit plan paused for human approval in both sessions. Exactly one Edit call followed each approval; local JSON checks passed. |
| Return to Ask | Goal, material facts, inspected evidence, unknowns and exhausted one-edit approval retained; zero further tool calls. |

Independent post-run comparison confirmed the complete synthetic JSON differed
only in the approved name, with no extra fixture files and the scope file
unchanged. Candidate vendor and installed-cache member hashes matched the
published release manifest. Recorded project configuration hashes were unchanged.
Native host skill-load messages, not model self-report alone, bound the loaded
copy. The exact seven partner prompts matched across runs.

No installation, observed handoff, approval-boundary or context-retention
regression was found in this exercise. Wording, documentation retrieval and
supporting-skill choices differed; this is not proof of universal factual
equivalence. The older installation also differed in content, so changes cannot
all be causally attributed to metadata alone.

## Separate GitHub-backed delivery observation

In a fresh project/test profile, the user installed the GitHub marketplace from
`main`. Supplied native plugin-detail screenshots showed `0.1.0`, enabled, at
project scope; after changing the same marketplace to the candidate branch and
running native updates, the screen showed `0.2.0-rc.1`, enabled, at project scope.
This is user-observed installed-version evidence, not an independently captured
second full behavior comparison. No uninstall/reinstall was prescribed.

## Structural checks and release gates

- 41 library tests passed on the candidate and were rerun during promotion.
- All 27 contracts, skill versions and catalog entries are checked; existing
  descriptions and 53 domain-reference hashes are regression guarded.
- Extracted filesystem profiles resolve without the original source checkout.
- The complete source-review archive is tested away from the source checkout.
- Native Claude plugin validation passed on the candidate with listing-only
  icon/privacy-URL warnings; publication does not invent claims to silence them.
- Release versions must agree across VERSION, both plugin manifests and the
  marketplace entry. Tag validation and tests run again in the release workflow.
- Merge remains subject to the repository's independent review and CI gates.

## Not run / not claimed

- Live Codex, Cursor or desktop-app behavior in this comparison.
- A live Docs-MCP-absent profile or fresh preference-consent profile (unit tests
  cover related logic, not actual host behavior).
- Real Salesforce org, package creation, deployment or production Act workflows.
- A downgrade/rollback execution; original data was backed up for recovery.
- Protected-filesystem isolation. Disabled discovery in an unrelated context
  does not establish that a candidate file cannot be read.
- An in-place update of standalone copied skills in another user's project.

Existing host plugins, hooks and configuration remained active; this was not a
clean-room environment. No private model reasoning was captured. Native output
and tool evidence were retained privately; none is represented here as a
public, independently reproducible certification.

the candidate surfaced an apparent Flex-template documentation conflict. These
are follow-up source/knowledge questions, not independently verified Salesforce
corrections or evidence that the metadata upgrade introduced a failure.

by users/admins; a custom invocation-time update notification was discussed but
is neither implemented nor claimed in this release.
